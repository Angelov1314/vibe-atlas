# Vibe Atlas 评分、社区与 Arena 实现说明

版本：2026-11-02.v1。本文参数是产品冷启动规则，不代表已用真实攻击样本训练或校准过的反作弊模型。

## 1. 三种榜单分别表达什么

| 指标 | 含义 | 无真实数据时 |
| --- | --- | --- |
| 可核验热度 | 可查证的 GitHub / X 关注度与维护活动 | 返回 null；缺项不补零、不编造社媒数据 |
| 社区质量 | 登录用户对使用体验的 1–5 分，经过权重和先验收缩 | 无票显示“待评价” |
| 模型 Arena | 同模态、同协议、同提示词的真实匿名输出偏好 | 无样本显示“等待真实盲评”，不给模型凭空设置1500分 |

热度不能被解释成能力、质量、许可证可用性或本机适配保证。通用网站工具与视频模型也不能共用一个“最强模型”榜。

## 2. 冷启动热度

可用信号的基本权重为：GitHub stars 45%、30日新增stars 20%、最近维护活动15%、90日贡献者10%、X 30日独立作者10%。

对于计数，先计算 `L(x) = 100 × clip(log(1+x) / log(1+anchor), 0, 1)`。参考锚分别为10万stars、1万月新增、100贡献者、1000名X作者。若有至少5个可比项目的同类候选集合，再取 `0.5 × L + 0.5 × 同类百分位`。并列值使用平均秩。细分类仅有一个候选时，不能把它自动叫作本类100分/第一名；可以使用更宽的父级类别或参考锚。

维护得分为 `100 × exp(-距最后push天数 / 180)`。它只是活跃度信号；稳定且无需频繁修改的工具可能被低估，用户应同时看到最近release与归档状态。后续可按领域校准这个分量。

实际得分 `S = Σ(可用权重 × 信号分数) / Σ可用权重`。覆盖率为已观测权重之和。置信指标为 `覆盖率 × exp(-快照距今天数 / 30)`；缺少快照时间仅使用0.4的保守新鲜度因子。它是数据完整性标记，不是统计置信概率。

例如只有stars数据时，覆盖率只有45%，不会暗示已经检查了增长、贡献者或X。榜单应同时展示数据日期与“45%信号已观测”。不同证据覆盖项目的排序只能视作探索顺序；不能宣称全网完整排名。

### GitHub数据约束

stars使用官方 API 的快照值，或官方网页显示的约数并保留 approximate 标志与核验日期。30日增长必须有至少两个真实历史快照，不能以项目年龄平均速度冒充。贡献者90日窗口必须通过历史提交或相应API核验，不能用总贡献者数替代。仓库重命名/转移要以canonical URL合并，镜像、模板派生与模型代码/权重必须区分。

### X数据约束

当前模块未接入X商业API或完整采集器。`xUniqueAuthors30d`默认缺失。只有在明确查询范围、时间窗、分页覆盖、URL匹配与去重规则的情况下才允许把`xWindowComplete`置为true。搜索引擎中的零星帖子可以作为证据链接，不足以计算“X全网第一”。零观测与未采集必须区分。

未来采集时宜按作者去重、限制单一作者贡献、去除重复转推与文本复制、记录独立域名引用、单独呈现原帖/二次传播，并抽样人工复核。蓝标不等于可信人类，互动量也不等于项目质量。

## 3. 社区评分与有效样本

数据库主键 `(item_id, identity_id)` 保证同一登录身份对同一项目只有一张当前票。再次提交更新原票，同时保留审计记录。浏览器发送的userId、weight和risk字段均不会被采用。身份以服务端HMAC持久化，数据库不存原始平台用户ID或原始IP。

每个评分档1–5使用相同Dirichlet先验，先验总强度12，均值3分。实际票权重被限制在0至1。加权后验使少量极端5分或1分不会瞬间把新项目推到榜首/榜底。

同时计算：

- `Σw`：等价完整票数。
- `n_Kish = (Σw)² / Σw²`：权重不均匀导致的信息损失指标。
- `n_info = min(Σw, n_Kish)`：用于后验的保守信息量。

必须限制在Σw以内，因为100个0.01权重的可疑账户，虽然Kish形式值为100，但只能贡献约1张完整票的证据。后验通过Dirichlet矩计算均值与近似95%区间；“近似”必须保留，分数不是针对真实总体随机抽样获得的精确置信声明。存在协同账号、相同社群或提示词聚类时仍可能低估相关性，后续需要聚类bootstrap。

默认按后验下界排序比按裸平均分稳健。低于20张等价有效票标注“初步”。无有效票完全不显示虚构的3.0/5社区评分，先验只存在于计算内部。

可选探索指数 `D=(1-λ)S+λC`，`λ=0.8×n_info/(n_info+50)`。这只是目录推荐顺序，必须同时显示独立热度、社区质量，不能把探索指数包装成Arena能力分。当前实现不会用GitHub热度作为社区先验，以免热度自我强化。

## 4. 已实现的防刷与边界

### 已实现

- 只有服务端可信平台身份可投票；严格Origin和JSON校验。
- HMAC身份键、SQL唯一票、原子计数器、审计轨迹。
- 每身份每分钟最多6次、每天最多40次投票尝试；限制包含重复修改，不以IP封禁共享网络。
- 新账号从0.45权重开始；站内年龄与经服务端核验的使用证据逐步提升，最高1。注册年龄只取本站first_seen，不假装知道平台账号年龄。
- 短时突增、重复序列、服务器确认的协同行为产生可解释风险分；高风险要求challenge，多个独立强信号可隔离而不计票。
- Turnstile服务器端验证success、hostname、action；secret缺失且本次需要验证时503失败关闭；验证失败不写入有效票。
- 隔离票保留原因和可申诉入口；管理员可恢复或驳回，并留痕。
- 管理员通过预配置ADMIN_USER_ID判定，绝不让首位访客自动成为管理员。

### 需要运营配置或后续数据

`challengeConfigured`只有真正配置Turnstile的sitekey和secret才为true。默认adaptive模式下，普通可信登录身份可在限速内评价；它不是“所有人都已通过人机验证”。`required`模式要求每张票验证，未配置时拒绝计票。

`loadCampaignSignals`为服务器检测器接口。没有接入检测器时`campaignAnalysisConfigured=false`，不能宣称已经自动识别投票团伙。当前代码不会凭前端字段或共享IP判断团伙，也没有暗中进行设备指纹跟踪。可逐步补充跨账号时序相关性、相似投票序列、来源异常、重复使用凭据与已确认滥用簇；所有规则需人工审查误报。

`verified_usage_count`不会因自己点一次“已安装”就增长。后续应接入可核验的成功运行收据/任务结果，并明确本地客户端提交仍可能造假。用户声誉不应仅根据是否与多数人一致来提高，否则会惩罚真实少数偏好。

不保证完全杜绝多账号、人工刷票、购买账号或高成本攻击。正式开放前应配置验证密钥与管理员、发布隐私/申诉规则、监控异常队列，并用真实攻击/正常使用数据校准参数。

## 5. Arena真实数据协议

`arena_protocols`保存模态与不可变协议哈希。协议定义应包含模型运行器、输出尺寸/时长/fps、精度、采样器/步数、引导参数、后处理、音频采样率/响度规范、硬件/驱动/软件版本、是否允许提示词重写等。不同任务和不同协议分别排名。

`arena_samples`要求模型ID和revision、protocol_hash、prompt_hash、实际文件SHA-256、R2 object_key、上传者、媒体类型/大小、参数JSON、公开授权和审核状态。默认pending；只有管理员确认来源、可比性、授权与输出完整性后才能变为verified。

`createArenaAssignment`只抽取同协议、同prompt、不同模型且双方verified/授权的真实样本，随机A/B顺序。模型ID、文件原路径和容易泄露模型身份的文件名不可提前显示；媒体通过带身份授权的opaque assignment代理提供。

`submitArenaVote`验证assignment归属、未过期、未揭盲、样本仍为verified且可比。SQL唯一约束还保证同一用户对同协议、同prompt、同一模型对只能贡献一次证据。提交后揭晓模型和revision。提供A/B/平局/都不好，“都不好”记录为失败信号，不自动伪装成平局。

初期实现可复算的时间序在线Elo，K=16，风险权重进入更新，明确标注provisional，不输出捏造的置信区间。不同连通分量不允许互相排名，零真实结果不生成榜单。`readArenaLeaderboard`每次再次过滤当前样本审核状态，撤销样本后旧票即时退出计分。

正式公开稳定榜建议采用协议内Bradley–Terry全量拟合、按用户和prompt的聚类bootstrap、发布数据覆盖和置信区间，并设每模型的对手覆盖、独立评委数和提示词数门槛。人类审美偏好、部署成功率、峰值显存、速度、许可证限制与成本应分别展示；没有跑过的本机性能不能写成实测。

## 6. 集成与测试

`ranking.ts`纯函数；`community.ts`D1服务；`schema.sql`可直接用于SQLite；`schema.ts`Drizzle声明供正式迁移生成。API请求调用者注入可信identity、origin、稳定的IDENTITY_HMAC_SECRET、项目白名单；adminSubject与Turnstile配置仅由服务器环境变量读取。

排名、社区、Arena、请求边界、采集器与检索的现有测试可用 `pnpm test` 执行；测试文件在 `tests/ranking.test.mjs` 和 `tests/retrieval.test.mjs`。本次公开版本的实际检查结果见 `docs/verification.md`。

测试使用真实内存SQLite，未声称生产Cloudflare资源已部署或真实Turnstile密钥已验证。最终部署与浏览器检查由站点主流程完成。
